Structure

Three layer schedules that do not tile. Exactly the kind the planner schema insists be written out rather than expressed as a repeating pattern.

Layer kindCountWhat it carries
compress_ratio 4 30 Overlapping Compressor plus Indexer
compress_ratio 128 31 Compressor only, no indexer
gate.tid2eid 3 Hash routing by token ID, layers 0 to 2, no learned gate
gate.bias 58 Learned routing, the remaining layers
mtp.0 1 Draft block, ratio 0, resident but outside the decode graph

compress_ratios has 62 entries, not 61. It is n_layers + n_mtp_layers, which resolves what first read as an off-by-one. The single 0 at index 61 is the MTP block, so all 61 backbone layers carry a compressor and exactly 30 carry an indexer. Both figures match the tensor census exactly.

Attention is MLA-style: num_key_value_heads: 1, head_dim: 512, with LoRA on both the query and the output projection (wo_a → wo_b, o_groups: 16). Residuals are mHC, Manifold-Constrained Hyper-Connections, where hc_split_sinkhorn runs 20 iterations at two sites per layer.

Per-GPU weights are not total / 8

model.py uses plain Linear, which is replicated, for wq_a, wkv, both compressors, and most expensively shared_experts (4.10 GB/GPU on its own). Only the parallel classes and the routed expert bank actually shard. The naive division gives 108.09 GB and understates the real figure by 6.46 GB. A plausible-looking number that is wrong in the direction that matters.

KV is small, and it is replicated

One KV head plus a plain-Linear wkv means every rank holds the full 512-dimension latent; sparse_attn takes local query heads against the complete cache. No TP division applies.

Uncompressed MLA at the same context would be 256 MB/seq, so the compressor buys ≈ 5.8×. Against 114.54 GB of weights, KV is a rounding error, which already says something about where the bound will land.

The 48 GB most accountings miss

FP4 scales are [out, in/32], full output resolution, unlike FP8's [out/128, in/128] blocks. They therefore cost 1/16 of expert weight bytes, not 1/16384: the expert bank is 773.71 GB of weights plus 48.36 GB of scale metadata.

Fit verdict

Stated as two numbers, because the case asks for the capacity lower bound and the configuration you would actually deploy to be distinguished. 

capacity LOWER BOUND     116.56 GB / 141 GB raw    FITS, 82.7% of capacity
deployable @ util 0.9    128.56 GB / 126.90 GB     −1.66 GB
What this number is not

The −1.66 GB shortfall is assumption-dominated: 12 GB of assumed workspace, communication buffers, and reserve against a 1.66 GB margin. It is not presented as a fact.

What is firm: 116.56 GB/GPU is fully derived, leaving 24.44 GB for workspace, communication, reserve, and fragmentation. Whether that suffices is an engine question, not a checkpoint question. Saying exactly that is worth more than a confident verdict with nothing under it.

If experts are converted to FP8

convert.py --expert-dtype fp8 adds +92.17 GB/GPU, taking weights alone to 206.71 GB against 141 GB. Impossible on one node. The minimal shape is two nodes at TP16 (≈107 GB/GPU); divisibility holds at 16 for experts, heads, o_groups, and vocabulary. That shape moves wo_b's all-reduce and the MoE all-reduce onto the inter-node fabric.

That comparison is drawn against weights alone, with no workspace and no reserve in the total, because the weights overflow on their own. Adding assumed numbers would make a guess load bearing in an argument that does not need one.

This is the first derived number that can be checked against something measured, and it lands in the right place. A roofline floor assumes perfect overlap and vendor peak, so it must sit above a real measurement. The 1.4x gap is where imperfect overlap, real bandwidth efficiency, and routing imbalance live.

The FP32 row worth a second look

FP32 is 2% of the FLOPs but 31% of the compute time, because the router and the mHC mixing run on CUDA cores at 67 TFLOP/s rather than on tensor cores. It does not matter at batch 32. It is the row that would matter first if batch grew.

Why the experts compute at BF16

The engine question that could have reordered everything, now resolved.

The routed experts are stored in MXFP4, the OCP MX format. That was confirmed independently from the checkpoint's own shapes: [out, in//2] in float4_e2m1fn_x2 with a scale of [out, in//32] in float8_e8m0fnu is exactly e2m1 values with one e8m0 scale per 32 elements.

H200 is SM90 and has no native FP4 tensor path, so the question is what vLLM does instead. The DeepSeek-V4 backend priority is FLASHINFER_TRTLLM_MXFP4_MXFP8, then DEEPGEMM_MXFP4, then MARLIN. The first two are Blackwell gated, so Hopper falls through to Marlin W4A16, which unpacks FP4 inside the kernel and multiplies in BF16.

Storage precision is not compute precision

Experts are stored at FP4 but computed at the BF16 rate of 989.5 TFLOP/s, not FP8's 1,979. Memory traffic stays at the FP4 rate. Only the math is slower. This is the third place in this model where the two diverge, and the one that matters most.

The FP8 escape hatch is closed twice over. The vLLM flag that would convert MXFP4 to block FP8 at load time lives in an open, unmerged PR, so it does not exist in v0.29.0. And it would add 92.17 GB per GPU, which does not fit.

One number from that PR validates the whole approach: converting to FP8 speeds up concurrent prefill by 2.04x but decode by only 1.13x. That gap is exactly what memory bound decode predicts, since doubling the bytes you read while speeding up the math roughly cancels out.

The three experiments

Each varies one engine knob and records one number the engine already reports. No profiler, no trace, no code change.

HypothesisVaryPredictedRejected if
E1 expert streaming dominates batch 1 → 64 2.6x step time for 32x batch within 1.3x, or above 8x
E2 launch is rank 2 graph on / off 2.5x ratio below 1.3x, or above 4x
E3 non-expert traffic is dense weights, not KV ctx 2k → 32k flat within 5% grows more than 15%

E3 is the sharpest claim in the note

On the 30 ratio-4 layers the indexer selects index_topk, which is 1,024 positions. Once context passes 4,096 there are more than 1,024 compressed slots, so the attention gather stops growing entirely. It is capped by index_topk, not by context. Only the ratio-128 layers and the indexer's own scan still scale, so quadrupling context from 8k to 32k adds under 3% to the step.

Each experiment also states what it cannot establish. E1 cannot separate bandwidth saturation from expert load imbalance, because both bend the curve the same way, and imbalance depends on what the tokens are.

Where communication sits, argued rather than assumed

On bandwidth it is trivial: 224.93 MB at 900 GB/s is 0.25 ms, under 2% of the step. On latency it may not be. There are 154 separate collectives, and a small-message all-reduce over NVLink has a floor around 5 to 10 microseconds regardless of payload. At 7 that is 1.08 ms, which would put it at rank 3.

So the honest answer is a range, 0.25 to 1.3 ms: fourth or fifth on bandwidth, third at worst, and never first, because rank 1 is 9.27 ms. Under the two-node TP16 shape it could plausibly lead, and that shape is not yet priced.

Checkpoint vs implementation

Three documented contradictions. Each one is evidence that storage, reference semantics, and execution are separate classes that must not be conflated.

1 · gate.tid2eid is stored int64; model.py declares int32

Derived, not assumed. At int32 the prediction fell exactly 9,308,160 B short, precisely 3 hash layers × 129,280 × 6 × 4 B, the int32→int64 delta on that one tensor. At int64 the reconciliation is exact.

2 · wo_a is FP8 in the checkpoint, loaded BF16 by the reference code

The Linear is constructed dtype=torch.bfloat16, yet attn.wo_a.scale appears 61 times in the index, and only FP8 and FP4 linears register scales. The vendor's own comment at model.py:539 confirms it. Storage precision ≠ runtime precision, stated by the vendor rather than inferred.

3 · No trust_remote_code path exists

No auto_map, no modeling_*.py. The inference/ folder is a standalone reference implementation requiring convert.py and torchrun, not an HF integration. vLLM runs its own in-tree implementation, so bound analysis must cite that, never inference/model.py.

Hardware divergence

A vendor recipe exists at recipes.vllm.ai/deepseek-ai/DeepSeek-V4-Pro, and the assignment says a published recipe supersedes the 8×H200 default. But the recipe targets 8 × AMD MI355X at 288 GB each, where the fit question becomes arithmetic with no tension in it.

Decision: price the assigned H200s and treat the divergence as a finding. The brief states the fit section carries the weight for V4-Pro, and that is only true at 141 GB. Choosing MI355X would satisfy the instruction's letter while deleting the section that carries the marks. The recipe's hardware-independent settings, --kv-cache-dtype fp8 and --gpu-memory-utilization 0.9, are adopted and cited.

What remains

D1, the planner-schema YAML

Not started. Follows gitm/planner/models/mimo-v2.5.yaml: layer schedules written out where they do not tile, per-op precision noted, checkpoint names kept verbatim, and family contradictions captured in comments rather than smoothed away.

Trim D2

The design note runs about 5,100 words against a one-to-two page ask. The case says match the reference note's rigor, not its length.

Three things that would change conclusions

  • Promote the Marlin claim to read-from-source. It currently rests on a PR description rather than merged source. If it is wrong, the expert GEMM ridge moves by 2x and hypothesis 1's compute side moves with it.
  • Count the kernels. The 4,326 figure is the softest number in the note and it carries rank 2. One profiler trace replaces the estimate with a count.
  • Settle whether collectives are latency bound. Recording NCCL time separately during E1's batch sweep would do it, since payload changes 32x while op count stays fixed. Flat means latency bound, scaling means bandwidth bound.

The one thing that cannot be derived

Expert load imbalance. The figure of 18.9 experts touched per rank assumes uniform routing, and real routing is not uniform. It depends on what the tokens are, so it needs a trace. Saying so is better than modelling it.

Neither requires a GPU, network access, or the weights themselves. They read only the metadata in context/checkpoint/.

Two evidence classes are kept separate throughout, because the case is explicit that conflating them is the failure mode: what the checkpoint establishes (shapes, counts, storage precision, layer schedules) versus what depends on the engine (fusion, launch behaviour, collective implementation, runtime precision). Every number carries its provenance. Every assumption is labelled rather than smuggled.
